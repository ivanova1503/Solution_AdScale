# AdScale — API Gateway для DSP-интеграции

## 1. Назначение

API Gateway обеспечивает безопасное и контролируемое подключение новой DSP-площадки к рекламной платформе AdScale.

Основные задачи:
- Приём OpenRTB-запросов от DSP.
- Аутентификация партнёра и проверка доступа.
- Ограничение частоты запросов (rate limiting).
- Маршрутизация запросов в AD Server.
- Защита от перегрузки и каскадных отказов.
- Мониторинг времени отклика и ошибок.

Gateway не содержит бизнес-логики расчёта ставок и выбора победителя. Эти функции выполняются внутренними сервисами AdScale.

## 2. Архитектура взаимодействия

```text
DSP Partner
    |
    | HTTPS / OpenRTB BidRequest
    v
+-----------------------------+
|         API Gateway         |
|-----------------------------|
| Authentication / mTLS       |
| Request validation          |
| Rate limiting               |
| Timeout / Circuit breaker   |
| Routing / Metrics           |
+-----------------------------+
    |
    | HTTPS or internal HTTP/gRPC
    v
+-----------------------------+
|           AD Server         |
+-----------------------------+
    |
    v
+-----------------------------+
| Auction Engine              |
|                             |
| Bidding logic (initially)   |
+-----------------------------+
    |
    v
 Auction result and BidResponse
    |
    v
API Gateway
    |
    | HTTPS / OpenRTB BidResponse
    v
DSP Partner
```

**Примечание:** на первом этапе логика расчёта ставок остаётся внутри Auction Engine. Выделение Bidding Service выполняется отдельно и не меняет внешнюю точку входа DSP.

## 3. Маршрутизация запросов

### 3.1. Внешний endpoint

| Параметр | Значение |
|---|---|
| Метод | `POST` |
| Путь | `/openrtb2/auction` |
| Протокол | HTTPS |
| Формат | OpenRTB BidRequest / BidResponse, JSON |
| Backend | AD Server |
| Таймаут | Настраивается в рамках общего SLA аукциона |

Пример маршрута:

`POST /openrtb2/auction → AD Server`

Gateway направляет запрос в AD Server после успешной аутентификации, проверки ограничений и базовой валидации.

### 3.2. Правила маршрутизации

- Запросы новой DSP направляются в соответствующий пул экземпляров AD Server.
- Конфигурация маршрута хранится отдельно от бизнес-логики AD Server.
- Проверяется размер запроса и корректность обязательных полей.
- Невалидные запросы отклоняются до попадания во внутренние сервисы.
- В запрос добавляется или сохраняется correlation ID для сквозной трассировки.
- Gateway не изменяет семантику OpenRTB-сообщений.

Маршрутизация по DSP может использовать отдельные credentials, политики rate limiting и настройки таймаутов.

## 4. Аутентификация и безопасность

Для каждого DSP-партнёра создаётся отдельная учётная запись интеграции.

### Основной механизм

API-ключ, передаваемый в заголовке `Authorization` или в согласованном служебном заголовке.

Пример:

```http
POST /openrtb2/auction HTTP/1.1
Host: ads.example.com
Content-Type: application/json
Authorization: Bearer <DSP_API_TOKEN>
X-Request-ID: req-123
```

Ключ используется для идентификации партнёра и применения его индивидуальных политик.

### Дополнительные меры

- HTTPS с TLS.
- mTLS для партнёров, которым требуется дополнительная проверка клиентского сертификата.
- Хранение секретов в защищённом хранилище, без записи в логи.
- Плановая ротация ключей и возможность немедленного отзыва.
- Ограничение доступа по IP, если это поддерживается соглашением с DSP.
- Проверка размера тела запроса и ограничение частоты запросов.
- Отсутствие персональных и секретных данных в диагностических логах.

Аутентификация подтверждает личность вызывающей стороны, а rate limiting ограничивает допустимую нагрузку. Эти механизмы решают разные задачи и должны использоваться совместно.

## 5. Rate limiting

Новая DSP увеличивает входящую нагрузку на платформу, поэтому Gateway должен ограничивать трафик партнёра и защищать внутренние сервисы.

### 5.1. Стратегия ограничений

Применяется алгоритм Token Bucket или эквивалентная реализация rate limiting.

Для каждого DSP задаются:
- Средняя допустимая скорость запросов — RPS.
- Допустимый размер кратковременного всплеска (burst).
- Максимальное количество одновременно обрабатываемых запросов.
- Общий лимит платформы, защищающий AD Server и Auction Engine.

Численные лимиты определяются после нагрузочного тестирования и согласования пропускной способности с DSP.

### 5.2. Поведение при превышении лимита

Если DSP превышает установленный лимит, Gateway отклоняет запрос до обращения к backend и возвращает HTTP `429 Too Many Requests`.

При необходимости ответ содержит `Retry-After`, если политика ограничения позволяет определить время повторной попытки.

Важно: автоматические повторы на стороне DSP не должны создавать новый всплеск нагрузки. Политика повторов и задержек согласуется в контракте интеграции.

### 5.3. Защита от перегрузки

Rate limiting дополняется:
- Лимитом одновременных запросов.
- Ограничением очередей и соединений.
- Таймаутами на обработку запроса.
- Ограничением размера запроса.
- Отдельными лимитами для партнёров и общим лимитом платформы.

Это позволяет защитить систему как от чрезмерной нагрузки одного партнёра, так и от суммарного превышения доступной мощности.

## 6. Circuit Breaker

Circuit Breaker защищает Gateway и внутренние сервисы от повторных запросов к backend, который не справляется с нагрузкой или стал недоступен.

### 6.1. Состояния

**CLOSED — нормальная работа**

Запросы направляются в AD Server. Gateway отслеживает таймауты и ошибки.

**OPEN — запросы временно блокируются**

При превышении настроенного порога ошибок Gateway прекращает отправлять запросы в проблемный backend на заданный интервал. Это предотвращает накопление зависших запросов и освобождает ресурсы.

**HALF-OPEN — проверка восстановления**

После периода ожидания пропускается ограниченное количество пробных запросов. Если backend отвечает успешно, Circuit Breaker возвращается в `CLOSED`; если ошибки продолжаются — снова переходит в `OPEN`.

### 6.2. Условия срабатывания

Возможные сигналы:
- Рост доли upstream-ошибок.
- Повторяющиеся таймауты.
- Недоступность экземпляров AD Server.
- Превышение заданного порога неуспешных запросов за временное окно.

Пороговые значения и длительность переходов определяются по результатам нагрузочного тестирования и эксплуатационных требований.

### 6.3. Поведение при открытом Circuit Breaker

Gateway должен быстро завершать запрос, не ожидая истечения полного таймаута.

Для DSP возвращается заранее согласованный ответ о невозможности обработки. Конкретный HTTP-статус и тело ответа определяются контрактом OpenRTB-интеграции. Нельзя автоматически подменять техническую ошибку фиктивным успешным результатом аукциона.

Автоматические повторы POST-запросов на ставки по умолчанию не выполняются: они могут увеличить нагрузку и привести к повторной обработке. Повторы допустимы только при явно определённых условиях и безопасной семантике операции.

**Важно:** Circuit Breaker Gateway защищает от отказов upstream-сервиса, но не заменяет Circuit Breaker, таймауты и контроль параллелизма внутри сервисов.

## 7. Мониторинг времени отклика

Gateway собирает метрики для контроля SLA и диагностики проблем на входе платформы.

### 7.1. Основные метрики

| Метрика | Назначение |
|---|---|
| `gateway_requests_total` | Количество запросов по DSP, маршруту и HTTP-статусу |
| `gateway_request_duration_seconds` | Время полного прохождения запроса через Gateway |
| `gateway_upstream_duration_seconds` | Время обработки запроса upstream-сервисом |
| `gateway_rate_limit_rejected_total` | Количество отклонённых запросов из-за rate limiting |
| `gateway_upstream_errors_total` | Ошибки при обращении к backend |
| `gateway_circuit_breaker_state` | Текущее состояние Circuit Breaker |
| `gateway_in_flight_requests` | Количество запросов в обработке |

Метрики времени отклика анализируются по перцентилям p50, p95 и p99, а также в разрезе DSP и маршрутов.

### 7.2. Алерты

Предусматриваются оповещения при:
- Превышении целевого p95/p99 latency.
- Росте доли upstream-ошибок и таймаутов.
- Частом открытии Circuit Breaker.
- Значительном увеличении числа ответов `429`.
- Исчерпании доступной пропускной способности.
- Росте количества запросов в обработке.

### 7.3. Трассировка

Для сквозной диагностики используется correlation ID / trace ID, который связывает запросы Gateway, AD Server и Auction Engine.

В логах фиксируются время обработки, маршрут, идентификатор DSP, результат аутентификации и статус ответа. Секреты, токены и ненужные персональные данные не записываются.

## 8. Реализация

В качестве API Gateway предлагается **Kong Gateway**.

Для реализации используются следующие возможности или эквивалентные механизмы выбранной версии и конфигурации:
- Маршрутизация по host/path/method.
- Аутентификация партнёров.
- Rate limiting и ограничения параллельных запросов.
- Таймауты и контроль соединений с upstream.
- Метрики и интеграция с системой мониторинга.
- TLS и, при необходимости, mTLS.

Circuit Breaker должен быть реализован средствами выбранного Gateway или прокси-слоя, если доступная конфигурация Kong не обеспечивает нужную семантику. В частности, обычные health checks и retry policy сами по себе не являются полноценным Circuit Breaker.

## 9. Критерии готовности

- Новая DSP может отправить корректный OpenRTB BidRequest через HTTPS.
- Неавторизованные запросы отклоняются.
- Превышение индивидуального лимита DSP приводит к контролируемому `429`.
- Запросы маршрутизируются в AD Server.
- При отказе backend Circuit Breaker предотвращает бесконтрольные вызовы.
- Время отклика Gateway и upstream измеряется отдельно.
- Настроены дашборды и алерты по задержкам, ошибкам и rate limiting.
- Проведены нагрузочные тесты, включая burst-нагрузку и отказ backend.
- Поведение при недоступности сервиса согласовано с DSP.

## 10. Итог

API Gateway становится контролируемой точкой входа для новой DSP-площадки. Он обеспечивает аутентификацию, ограничение нагрузки, маршрутизацию, защиту от каскадных отказов и наблюдаемость, при этом не вмешивается в бизнес-логику аукциона.

Kong Gateway выбран как исходный вариант реализации; конкретные лимиты, таймауты, пороги Circuit Breaker и SLA фиксируются после нагрузочного тестирования и согласования с DSP.
