# AdScale — Interaction Design

## 1. Цель

Определить протоколы и паттерны взаимодействия между компонентами AdScale с учётом требований к производительности аукциона, масштабируемости и отказоустойчивости.

Ключевые требования:
- Минимизировать задержку обработки рекламного запроса.
- Поддерживать рост нагрузки со стороны DSP.
- Исключить влияние статистики и аналитики на критический путь аукциона.
- Обеспечить надёжную доставку событий кликов и показов.
- Изолировать внутренние сервисы от внешнего трафика.

## 2. Выбор протоколов

| Взаимодействие | Протокол / паттерн | Обоснование |
|---|---|---|
| DSP → API Gateway → AD Server | HTTPS / OpenRTB | Стандартный протокол рекламной интеграции |
| AD Server → Auction Engine | gRPC | Низкие накладные расходы и типизированный контракт |
| Auction Engine → Bidding Service | gRPC | Синхронный расчёт ставки в критическом пути аукциона |
| Campaign Management → Bidding Service | Kafka events + локальный кэш; REST для управления | Не требуется синхронный запрос к Campaign Management при каждом расчёте ставки |
| Advertiser Dashboard → API Gateway | HTTPS / REST | Удобный контракт для веб-клиента и операций управления |
| Auction Engine → Financial Service | gRPC, если требуется синхронная проверка или резервирование бюджета | Контролируемая задержка и явный контракт финансовой операции |
| AD Server / Delivery Service → Event Broker | Kafka | Асинхронная публикация событий |
| Event Broker → Statistics / Analytics | Kafka consumers | Независимое масштабирование обработки событий |
| Сервисы → Monitoring | Метрики, логи, трассировка | Контроль задержек, ошибок и доступности |

## 3. Внутреннее взаимодействие

### 3.1. Bidding Service — gRPC

Для взаимодействия Auction Engine с Bidding Service выбирается **синхронный gRPC**.

Расчёт ставки должен завершиться до того, как Auction Engine сможет принять решение о победителе. Поэтому полностью асинхронный вызов здесь неудобен: он добавил бы ожидание ответа через брокер, усложнил корреляцию запросов и обработку таймаутов.

Преимущества gRPC:
- Protobuf обеспечивает строгую типизацию и версионируемый контракт.
- HTTP/2 позволяет эффективно обрабатывать большое количество запросов.
- Поддерживаются deadlines, статусы ошибок и механизмы отмены вызова.
- Клиентские и серверные интерфейсы генерируются из единого контракта.

Основной метод:

`CalculateBid(request) → BidResponse`

В ответе возвращается ставка либо штатный результат `NO_BID`.

**Ограничения:** gRPC не гарантирует низкую задержку сам по себе. Результат зависит от сетевой топологии, сериализации, загрузки сервиса и базы данных. Для критического пути необходимо задавать таймауты и контролировать p95/p99.

### 3.2. Campaign Management — REST и события

Для API управления кампаниями выбирается **REST/HTTPS**. Он подходит для административных операций: создания и изменения кампаний, настройки бюджетов и правил, получения текущей конфигурации.

Однако Bidding Service не должен выполнять REST-запрос в Campaign Management при каждом расчёте ставки. При высокой нагрузке это создаст дополнительную сетевую задержку и зависимость от доступности другого сервиса.

Рекомендуемый подход:
1. Campaign Management сохраняет изменения в собственной базе.
2. После успешного изменения публикует событие `CampaignConfigUpdated` в Kafka.
3. Bidding Service получает событие и обновляет локальную копию конфигурации или кэш.
4. При расчёте ставки сервис использует локально доступные данные.

Пример события:

```json
{
  "eventId": "evt-123",
  "eventType": "CampaignConfigUpdated",
  "campaignId": "cmp-789",
  "version": 12,
  "occurredAt": "2026-10-10T12:00:00Z",
  "config": {
    "status": "ACTIVE",
    "baseBid": 1.25,
    "currency": "EUR"
  }
}
```

Для восстановления после потери или устаревания конфигурации предусматривается возможность повторной синхронизации через API Campaign Management.

Таким образом, REST используется для управления и восстановления данных, а события — для своевременного распространения изменений.

## 4. Внешняя интеграция с DSP

Для взаимодействия с DSP используется **OpenRTB поверх HTTPS**. OpenRTB определяет формат рекламного запроса и ответа, включая параметры аукциона и ставки.

Основной поток:

1. DSP отправляет `BidRequest` в API Gateway.
2. Gateway проверяет доступ, лимиты и корректность запроса.
3. Запрос маршрутизируется в AD Server.
4. AD Server формирует кандидатов и передаёт их в Auction Engine.
5. Auction Engine получает результаты расчёта ставок от Bidding Service и определяет победителя.
6. AD Server возвращает DSP `BidResponse` через API Gateway.

Для типичного OpenRTB 2.x взаимодействия используется HTTP POST с JSON. Конкретные версии спецификации, обязательные поля и расширения необходимо согласовать с каждым DSP.

Требования к внешнему контракту:
- Соблюдение выбранной версии OpenRTB.
- Проверка входных данных и ограничение размера запроса.
- Контроль таймаутов с учётом SLA аукциона.
- Корректная обработка невалидных запросов и ситуации отсутствия подходящей ставки.
- Аутентификация DSP и защита от чрезмерной нагрузки.

Gateway не должен выполнять бизнес-логику расчёта ставки или выбора победителя.

## 5. API Gateway

**API Gateway необходим** как отдельный инфраструктурный компонент на границе внешнего доступа к платформе.

Для AdScale можно рассмотреть **Envoy Gateway** или **Kong Gateway**. Оба варианта поддерживают основные задачи входного шлюза. Для исходного проектного решения предлагается Kong Gateway как готовый API Gateway с политиками доступа и ограничениями запросов; Envoy также подходит, если инфраструктура команды уже основана на его экосистеме.

### Функции Gateway

- **Rate limiting:** ограничения запросов по DSP, клиенту, ключу доступа или другому идентификатору.
- **Аутентификация и авторизация:** проверка ключей, токенов или сертификатов в зависимости от соглашения с партнёром.
- **Маршрутизация:** передача OpenRTB-запросов в AD Server, а запросов управления — в соответствующие API.
- **Валидация:** проверка базовых требований к формату и размеру запроса.
- **Таймауты:** ограничение времени обработки внешнего запроса.
- **Наблюдаемость:** сбор RPS, latency, ошибок и количества отклонённых запросов.
- **Защита:** TLS termination, ограничения соединений и базовые механизмы противодействия перегрузке.

Gateway не должен находиться между каждым внутренним сервисом. В частности, вызов AD Server → Auction Engine → Bidding Service выполняется по внутренней сети, чтобы не добавлять лишние переходы на критическом пути аукциона.

### Принципиальное ограничение

Rate limiting на Gateway защищает платформу от превышения согласованной нагрузки, но не заменяет внутреннюю защиту от перегрузки. Bidding Service и Auction Engine также должны иметь собственные лимиты параллелизма, таймауты и механизмы контролируемого отказа.

## 6. Потоковая обработка событий — Kafka

Для кликов, показов и результатов аукционов используется **Apache Kafka**.

Эти события не требуют синхронного ответа от Statistics Service или Analytics Service в момент обработки рекламного запроса. Поэтому их публикация через брокер позволяет отделить критический путь аукциона от фоновой обработки.

### Основные события

- `ImpressionRecorded` — зафиксирован показ рекламы.
- `ClickRecorded` — зафиксирован клик.
- `AuctionCompleted` — завершён аукцион.
- `BidCalculated` — рассчитана ставка.
- `FinancialTransactionRecorded` — зафиксирована финансовая операция.

### Поток обработки

1. Источник события публикует сообщение в Kafka.
2. Kafka сохраняет сообщение и делает его доступным потребителям.
3. Statistics Service обрабатывает события кликов и показов.
4. Analytics Service независимо обрабатывает события для агрегатов и отчётности.
5. При временной недоступности потребителя сообщения остаются доступными для последующей обработки в пределах настроенной политики хранения.

### Почему Kafka

- Разделяет скорость публикации и скорость обработки событий.
- Позволяет масштабировать потребителей независимо от источников.
- Поддерживает повторное чтение событий и восстановление обработки.
- Позволяет нескольким группам потребителей независимо читать один поток.
- Буферизует всплески нагрузки.

Kafka не обеспечивает автоматическую сквозную обработку «ровно один раз» для любой бизнес-операции. Поэтому потребители должны быть идемпотентными, а политика повторной обработки — явно определённой.

### Требования к надёжности

- Ключ сообщения выбирается с учётом порядка обработки; например, `campaignId` или `auctionId` в зависимости от события.
- События получают уникальный `eventId`.
- Потребители защищаются от повторной обработки.
- Для повторных ошибок предусматриваются ограниченные повторы и DLQ (dead-letter queue).
- Настраиваются replication factor, retention, мониторинг consumer lag и алерты.
- Если требуется гарантированно публиковать событие после записи в базе данных, рассматривается паттерн Transactional Outbox.

Kafka используется для событийной интеграции, а не как замена синхронному API расчёта ставки.

## 7. Паттерны взаимодействия

### Синхронный Request–Response

Используется там, где вызывающая сторона не может продолжить работу без результата:
- AD Server → Auction Engine.
- Auction Engine → Bidding Service.
- Финансовая проверка или резервирование бюджета, когда она необходима для корректности решения.

Для каждого вызова задаются таймауты и правила обработки ошибок. Повторные вызовы допустимы только там, где они безопасны с точки зрения бизнес-операции.

### Event-Driven Architecture / Publish–Subscribe

Используется для распространения изменений конфигурации и обработки событий:
- Обновление конфигурации кампаний.
- События показов, кликов и завершения аукциона.
- Передача данных в статистику и аналитику.

Потребители обрабатывают события независимо друг от друга.

### Cache-Aside / локальная конфигурация

Bidding Service хранит актуальную рабочую копию конфигурации ставок. Обновления приходят через события, а при обнаружении устаревших данных сервис может инициировать повторную синхронизацию.

Необходимо определить допустимую задержку распространения изменений и поведение при недоступности источника конфигурации.

### Circuit Breaker и Bulkhead

Для вызовов зависимых сервисов применяются ограничение параллелизма и защита от каскадных отказов. Circuit breaker должен использоваться осознанно: например, отключение финансовой зависимости не должно автоматически разрешать ставки при неизвестном состоянии бюджета.

## 8. Требования к задержкам и SLA

Целевой SLA рекламного аукциона составляет 80 мс. Этот бюджет включает сетевые переходы, подбор кандидатов, расчёт ставок, выбор победителя и формирование ответа.

Рекомендуемые принципы:
- Минимизировать количество синхронных сетевых вызовов.
- Не выполнять тяжёлые аналитические запросы в критическом пути.
- Не обращаться к Campaign Management за конфигурацией на каждый запрос.
- Измерять p95 и p99 отдельно для Gateway, AD Server, Auction Engine и Bidding Service.
- Согласовать таймауты компонентов так, чтобы суммарная задержка укладывалась в бюджет SLA.
- Проводить нагрузочные тесты с целевым RPS и резервом пропускной способности.

Конкретные внутренние бюджеты задержек определяются по результатам профилирования и нагрузочных тестов, а не только на основании выбора протокола.

## 9. Итоговое решение

- **Bidding Service:** синхронный gRPC для расчёта ставки.
- **Campaign Management:** REST для управления, Kafka для распространения изменений конфигурации, локальный кэш в Bidding Service.
- **DSP:** OpenRTB поверх HTTPS через API Gateway.
- **API Gateway:** Kong Gateway как исходный вариант для внешней точки входа, rate limiting, аутентификации и маршрутизации.
- **События:** Kafka для кликов, показов, результатов аукционов и аналитических потоков.
- **Внутренняя сеть:** прямые сервисные вызовы между доверенными внутренними компонентами, без обязательного прохождения через Gateway.

Такое разделение сохраняет синхронность там, где нужен немедленный результат, и использует асинхронную обработку там, где важнее изоляция нагрузки, масштабируемость и устойчивость.
