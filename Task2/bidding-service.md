# Bidding Service — спецификация сервиса ставок

## 1. Назначение

**Bidding Service** — микросервис AdScale, отвечающий за расчёт размера ставки для рекламного кандидата в рамках аукциона.
Эта логика выделяется в самостоятельный сервис с собственной базой данных.

Цели выделения:
- Независимое горизонтальное масштабирование расчёта ставок.
- Снижение нагрузки на Auction Engine.
- Изоляция критичного пути аукциона от статистики и аналитики.
- Повышение отказоустойчивости при росте нагрузки от DSP.

## 2. Границы ответственности

- Расчёт ставки.
- Проверка правил.
- Возврат результата расчёта.
- Публикация событий о результатах расчёта для последующей аналитики.

Bidding Service рассчитывает предложение для участия в аукционе, но не определяет победителя и не выполняет финансовое списание.

## 3. API сервиса

Для критичного пути аукциона предпочтителен gRPC с Protobuf

### Расчёт ставки

**Метод:** `CalculateBid`
**Вызывающая сторона:** Auction Engine.
**Назначение:** рассчитать ставку для рекламного кандидата и вернуть результат.
Пример запроса:

```json
{
  "requestId": "req-123",
  "auctionId": "auc-456",
  "campaignId": "cmp-789",
  "placementId": "placement-22",
  "floorPrice": 0.5,
  "currency": "EUR",
  "context": {
    "country": "NL",
    "device": "desktop"
  }
}
```

Пример успешного ответа:

```json
{
  "requestId": "req-123",
  "auctionId": "auc-456",
  "campaignId": "cmp-789",
  "status": "BID",
  "bidPrice": 1.25,
  "currency": "EUR",
  "ruleVersion": 12,
  "reason": "ELIGIBLE"
}
```
## 4. Зависимости от других сервисов

| Сервис | Тип взаимодействия | Назначение |
|---|---|---|
| Auction Engine | Синхронный gRPC | Передаёт кандидата и получает рассчитанную ставку |
| Сервис управления кампаниями | API и/или события | Передаёт настройки кампаний и изменения конфигурации |
| Financial Service | События и согласованный API | Передаёт состояние бюджета; при необходимости обеспечивает проверку или резервирование средств |
| Event Broker (Kafka) | Асинхронно | Доставка событий расчёта ставок для аналитики |
| Analytics Service | Через Event Broker | Анализ результатов ставок вне критичного пути |
| Monitoring | Метрики, логи и трассировка | Наблюдаемость и контроль SLA |

### Принципы взаимодействия

1. **Нет прямого доступа к чужим базам данных.** Bidding Service читает собственную базу. Данные кампаний и бюджета получает через API или события.
2. **Минимум синхронных вызовов.** Настройки кампаний и правила заранее загружаются в локальный кэш, чтобы не обращаться к другим сервисам при каждом расчёте.
3. **Финансовая корректность.** Кэш бюджета не гарантирует отсутствие перерасхода. Если требуется строгое соблюдение лимита, Financial Service должен предоставлять механизм атомарного резервирования или другой согласованный способ подтверждения доступных средств.
4. **Асинхронная аналитика.** Результаты расчёта публикуются в Kafka; недоступность аналитических потребителей не должна блокировать выдачу ставки.
5. **Защита от перегрузки.** Для зависимостей задаются таймауты, лимиты параллелизма и контролируемое поведение при отказах.

## 5. Модель данных

Bidding Service владеет собственной базой PostgreSQL. В ней хранятся настройки расчёта и правила ставок. Финансовые балансы и мастер-данные кампаний остаются у соответствующих сервисов.

### 5.1. `campaign_bid_config`

Основная конфигурация ставок по кампаниям.

| Поле | Тип | Назначение |
|---|---|---|
| `campaign_id` | UUID / VARCHAR | Первичный ключ, идентификатор кампании |
| `base_bid` | NUMERIC(18, 6) | Базовая ставка |
| `currency` | CHAR(3) | Код валюты |
| `min_bid` | NUMERIC(18, 6) | Минимальная допустимая ставка |
| `max_bid` | NUMERIC(18, 6) | Максимальная допустимая ставка |
| `status` | VARCHAR | Состояние конфигурации |
| `rule_version` | INTEGER | Текущая версия правил |
| `updated_at` | TIMESTAMPTZ | Время последнего изменения |

`campaign_id` является внешним бизнес-идентификатором. Внешний ключ на таблицу другого сервиса не создаётся.

### 5.2. `bid_rules`

Правила корректировки ставки.

| Поле | Тип | Назначение |
|---|---|---|
| `rule_id` | UUID | Первичный ключ |
| `campaign_id` | UUID / VARCHAR | Идентификатор кампании |
| `condition_type` | VARCHAR | Тип условия применения |
| `condition_value` | JSONB | Параметры условия |
| `multiplier` | NUMERIC(10, 6) | Коэффициент корректировки |
| `priority` | INTEGER | Приоритет применения правила |
| `is_active` | BOOLEAN | Признак активности |
| `valid_from` | TIMESTAMPTZ | Начало действия |
| `valid_to` | TIMESTAMPTZ | Окончание действия |

Индекс предусматривается по `campaign_id` и признаку активности. Правила одной кампании применяются в определённом и документированном порядке.

### 5.3. `budget_snapshot`

Локальное представление бюджетных ограничений, если оно требуется для быстрого расчёта.

| Поле | Тип | Назначение |
|---|---|---|
| `campaign_id` | UUID / VARCHAR | Первичный ключ |
| `available_budget` | NUMERIC(18, 6) | Последнее известное доступное значение |
| `currency` | CHAR(3) | Код валюты |
| `source_version` | VARCHAR | Версия данных источника |
| `as_of` | TIMESTAMPTZ | Время получения данных |
| `valid_until` | TIMESTAMPTZ | Срок актуальности |

Эта таблица не является источником истины о деньгах. При истечении срока актуальности snapshot сервис действует согласно политике бюджета: например, отклоняет ставку или обращается за подтверждением в Financial Service. Выбор политики зависит от бизнес-требований.

### 5.4. `bid_decisions`

Журнал результатов расчёта ставок.

| Поле | Тип | Назначение |
|---|---|---|
| `decision_id` | UUID | Первичный ключ |
| `request_id` | VARCHAR | Идентификатор запроса |
| `auction_id` | VARCHAR | Идентификатор аукциона |
| `campaign_id` | UUID / VARCHAR | Идентификатор кампании |
| `status` | VARCHAR | `BID` или `NO_BID` |
| `bid_price` | NUMERIC(18, 6) | Рассчитанная ставка |
| `currency` | CHAR(3) | Код валюты |
| `reason` | VARCHAR | Причина результата |
| `rule_version` | INTEGER | Версия правил, использованная при расчёте |
| `created_at` | TIMESTAMPTZ | Время расчёта |

### 5.5. Связи сущностей: 
- campaign_bid_config — одна конфигурация на кампанию.
- bid_rules — несколько правил на одну кампанию.
- budget_snapshot — необязательная локальная копия бюджетных данных.
- bid_decisions — множество результатов расчёта по кампаниям и аукционам.
Все финансовые суммы хранятся в NUMERIC, а не в FLOAT, чтобы избежать ошибок округления.
