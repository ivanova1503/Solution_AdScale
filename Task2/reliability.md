# AdScale — Паттерны надёжности

## 1. Цель

Цель — повысить устойчивость AdScale к временной недоступности сервисов, сетевым ошибкам, перегрузкам и повторной доставке запросов.

В качестве основных механизмов используются:

- **Circuit Breaker** — предотвращение каскадных отказов.
- **Retry с экспоненциальной задержкой** — восстановление после временных ошибок.
- **Idempotency** — защита от повторного выполнения финансовых операций.
- **Fallback** — продолжение обслуживания запросов при недоступности отдельных компонентов.

Эти механизмы применяются с учётом критичности операций и требований к задержке рекламного аукциона.

## 2. Circuit Breaker для зависимых сервисов

Circuit Breaker применяется при синхронных вызовах между сервисами, например:

- AD Server → Auction Engine;
- Auction Engine → Bidding Service после его выделения;
- Auction Engine → Financial Service при проверке доступного рекламного бюджета;
- Advertiser Dashboard → Financial Service;
- Advertiser Dashboard → Analytics Service.

### 2.1. Состояния паттерна

| Состояние | Поведение |
|---|---|
| `CLOSED` | Запросы выполняются штатно, ошибки учитываются |
| `OPEN` | Вызовы проблемного сервиса временно блокируются |
| `HALF-OPEN` | Выполняется ограниченное число проверочных запросов для определения восстановления |

Переход в `OPEN` происходит, когда доля ошибок или число таймаутов превышают заданный порог за определённый интервал. После периода ожидания Circuit Breaker переходит в `HALF-OPEN`.

Пороги, временные окна и длительность блокировки определяются нагрузочным тестированием и эксплуатационными требованиями.

### 2.2. Поведение при сбое

Если Auction Engine перестаёт отвечать, AD Server не должен бесконечно ждать завершения запроса. Вызов завершается по таймауту, а Circuit Breaker временно прекращает новые обращения к проблемному компоненту.

При этом поведение зависит от операции:

- Для критичного пути аукциона запрос завершается в пределах установленного бюджета времени, если получить результат невозможно.
- Для аналитики допускается отложенная обработка или временная недоступность отчётов.
- Для финансовых операций нельзя автоматически считать проверку баланса успешной только потому, что Financial Service недоступен.

Circuit Breaker не заменяет таймауты и ограничения параллелизма: все три механизма должны применяться совместно.

## 3. Повторные попытки с экспоненциальной задержкой

Retry используется для восстановления после временных ошибок: кратковременного разрыва соединения, временной перегрузки или недоступности сетевого узла.

### 3.1. Алгоритм

Между повторными попытками увеличивается время ожидания:

\[
t_n = \min(t_{\max}, t_0 \cdot 2^n)
\]

где:

- \(t_0\) — начальная задержка;
- \(n\) — номер повторной попытки, начиная с нуля;
- \(t_{\max}\) — максимальная задержка.

Для предотвращения одновременных повторов большого количества клиентов добавляется случайный разброс (*jitter*).

Пример конфигурации для фоновых операций:

- начальная задержка — 100 мс;
- множитель — 2;
- максимальная задержка — 2 секунды;
- не более 3 повторов;
- общий срок выполнения ограничен дедлайном операции.

Эти значения являются стартовыми параметрами и требуют настройки под конкретный сервис.

### 3.2. Когда повторять запросы

**Допустимые случаи:**
- временные сетевые ошибки;
- ограниченный набор ответов `5xx`;
- `429 Too Many Requests`, если предусмотрена задержка по `Retry-After`;
- временная недоступность брокера сообщений при публикации события.

**Не следует повторять автоматически:**
- ошибки валидации `4xx`;
- ошибки аутентификации и авторизации;
- запросы, для которых неизвестно, успела ли выполниться операция с побочным эффектом, если отсутствует защита от повторного выполнения;
- вызовы, у которых уже исчерпан дедлайн.

### 3.3. Особенности критического пути ставок

В рекламном аукционе задержка непосредственно влияет на вероятность получения ответа DSP. Поэтому количество повторов на синхронном пути должно быть минимальным.

Если запрос к Bidding Service не успевает выполниться в пределах дедлайна, система должна использовать допустимую резервную стратегию либо завершить запрос без ставки. Длительные повторы недопустимы.

Для асинхронных событий Kafka допускаются повторные попытки с увеличивающейся задержкой и последующим переносом необрабатываемых сообщений в Dead Letter Queue (DLQ).

## 4. Идемпотентность финансовых операций

Финансовые операции требуют особой защиты: повтор одного запроса не должен приводить к повторному списанию средств или повторному зачислению бюджета.

### 4.1. Механизм

Каждая финансовая операция получает уникальный `Idempotency-Key`. Ключ сохраняется в Financial Service вместе с результатом операции.

Пример запроса:

```http
POST /api/v1/balance/top-up
Authorization: Bearer <token>
Idempotency-Key: topup-8f2c1a
Content-Type: application/json
```

Пример тела:

```json
{
  "accountId": "account-123",
  "amount": 5000,
  "currency": "RUB"
}
```

При первом запросе Financial Service проверяет операцию, выполняет её и сохраняет результат. При повторном запросе с тем же ключом и теми же параметрами возвращается ранее сохранённый результат без повторного изменения баланса.

### 4.2. Требования к реализации

1. Уникальность `Idempotency-Key` обеспечивается ограничением в базе данных.
2. Запись ключа операции, изменение баланса и сохранение результата выполняются согласованно в рамках транзакции.
3. Повторное использование ключа с другим набором параметров отклоняется.
4. Параллельные запросы с одинаковым ключом не должны выполнять списание дважды.
5. Ключи хранятся достаточно долго для обработки повторов и восстановления после сбоев.
6. При интеграции с платёжным шлюзом применяется согласованный идентификатор операции и механизм сверки статусов.

Если платёжный шлюз выполнил платёж, но ответ потерялся в сети, Financial Service не должен без проверки запускать новое списание. Он использует тот же идентификатор операции, запрашивает статус платежа или выполняет сверку.

**Важно:** идемпотентность сама по себе не гарантирует атомарность между базой Financial Service и внешним платёжным шлюзом. Для согласованности применяются сохранение состояния операции, повторная проверка статуса и, при необходимости, компенсационные действия.

### 4.3. Обработка финансовых событий

Для событий Kafka, например `BudgetDebited` или `PaymentConfirmed`, потребители также должны быть идемпотентными.

Каждое событие содержит уникальный `eventId`. Перед применением изменений потребитель проверяет, не обрабатывалось ли событие ранее. Фиксация факта обработки и бизнес-изменения выполняется согласованно.

Это предотвращает повторное изменение баланса при повторной доставке сообщения.

## 5. Резервные стратегии (Fallback)

Fallback позволяет сохранить часть функциональности при недоступности зависимых компонентов. Стратегия выбирается отдельно для каждого сценария.

### 5.1. Кешированные данные кампаний

Если Campaign Management или хранилище конфигурации недоступны, Bidding Service может использовать последнюю успешно полученную конфигурацию кампаний из локального кеша.

Условия применения:

- Конфигурация была предварительно проверена и сохранена.
- У данных есть версия и время последнего обновления.
- Определён максимальный срок допустимой устарелости.
- Обновления доставляются через Kafka или другой механизм распространения конфигурации.
- После восстановления соединения выполняется синхронизация.

Кеш кампаний подходит для параметров подбора рекламы, но не должен использоваться как единственный источник истины для актуального финансового баланса.

### 5.2. Кешированные ставки

Предварительно рассчитанные ставки можно использовать только для тех сценариев, где бизнес-правила допускают ограниченно устаревший результат.

Перед применением проверяются срок действия, версия кампании, ограничения таргетинга и актуальность доступного бюджета. Если безопасность или корректность результата не подтверждены, кешированная ставка не используется.

Для персонализированных аукционов кеширование полного результата ставки может быть небезопасным: запросы отличаются контекстом, ценой, таргетингом и ограничениями кампаний.

### 5.3. Дефолтная ставка

Для отдельных сценариев может быть предусмотрена заранее согласованная дефолтная ставка. Она применяется только если это допускают контракт с DSP и бизнес-правила AdScale.

Обязательные ограничения:

- ставка находится в пределах допустимого ценового диапазона;
- проверены актуальные ограничения кампании и бюджета;
- отсутствуют нарушения таргетинга и другие ограничения показа;
- использование дефолтной ставки учитывается в метриках.

Если актуальность бюджета или право на показ подтвердить нельзя, безопаснее вернуть ответ без ставки, чем сформировать некорректное финансовое обязательство.

### 5.4. Резервная стратегия для финансовых сервисов

Для Financial Service не используется стратегия «разрешить операцию по умолчанию».

Если актуальный баланс недоступен, новая операция списания или резервирования бюджета не должна считаться успешной без подтверждения. Можно временно приостановить соответствующую операцию и повторить её после восстановления сервиса.

Таким образом, допустимая деградация для рекламного аукциона и финансовой подсистемы различается: для аукциона возможен ограниченный fallback, а для финансовых операций приоритетом остаётся корректность данных.

## 6. Сводная таблица

| Ситуация | Механизм | Поведение AdScale |
|---|---|---|
| Auction Engine недоступен | Timeout + Circuit Breaker | Не ждать бесконечно; использовать допустимый fallback или завершить запрос без ставки |
| Временная сетевая ошибка | Retry + backoff + jitter | Ограниченное число повторов в пределах дедлайна |
| Campaign Management недоступен | Локальный кеш | Использовать актуальную версию кеша в пределах установленного срока |
| Нет актуальной ставки | Проверенный fallback | Использовать допустимую дефолтную ставку или не участвовать в аукционе |
| Повторный запрос на пополнение | Idempotency-Key | Вернуть прежний результат без повторного зачисления |
| Потерян ответ платёжного шлюза | Проверка статуса операции | Сверить результат, не инициировать бездумно новый платёж |
| Повторная доставка события Kafka | Идемпотентный consumer | Не применять одно финансовое событие повторно |
| Analytics Service недоступен | Kafka + Retry + DLQ | Сохранять события для последующей обработки, если брокер и политика хранения позволяют |

## 7. Мониторинг и проверка надёжности

Необходимо контролировать:
- количество переходов Circuit Breaker в состояние `OPEN`;
- число повторных попыток и долю успешно восстановленных запросов;
- таймауты и ошибки зависимых сервисов;
- количество ответов без ставки и использование fallback;
- число повторных финансовых запросов и конфликтов ключей идемпотентности;
- возраст кешированной конфигурации;
- количество повторно обработанных событий и размер DLQ;
- задержку обработки сообщений Kafka.

Для проверки проводятся нагрузочные тесты и fault injection: отключение зависимого сервиса, задержка ответов, потеря соединения после выполнения финансовой операции, повторная доставка Kafka-события и резкий всплеск входящего трафика.

## 8. Итог

Надёжность AdScale обеспечивается сочетанием нескольких паттернов: Circuit Breaker ограничивает влияние отказов, Retry с экспоненциальной задержкой помогает переживать временные ошибки, идемпотентность защищает финансовые операции от повторного выполнения, а Fallback позволяет сохранять ограниченную работоспособность рекламного аукциона.

При этом система не должна жертвовать корректностью финансовых данных ради доступности: если актуальность баланса или право на списание подтвердить невозможно, операция приостанавливается до восстановления достоверного состояния.
