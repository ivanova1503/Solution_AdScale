### Решение: 
Микросервисная архитектура с границами по доменам: 
- AD‑сервер, Auction Engine, Financial и другие ключевые сервисы — как отдельные микросервисы со своими жизненными циклами и деплоем.
- Database per Service: у каждого критичного сервиса — своя БД, чтобы убрать блокировки строк и конкуренцию за ресурсы.
- Событийная модель (Event‑Driven) на базе брокера (Kafka/RabbitMQ): постоянный поток событий уходит в брокер; сервисы реагируют асинхронно, снижая синхронную нагрузку и таймауты.
- Разделение потоков: критичные (ставки, списание средств, SLA < 80 мс) и некритичные (аналитика, дашборды) потоки обрабатываются разными очередями.
- Кэширование и репликация для чтения: Redis для горячих данных и read‑replicas для тяжёлой аналитики.
- Горизонтальное масштабирование: автоскейлинг для ключевых сервисов; возможность быстро добавлять инстансы под пиковые нагрузки.
- Мультирегиональное развёртывание: минимум два региона с распределением трафика; failover между регионами для доступности 99,9%.
- Буферизация и контроль нагрузки: буфер событий и пакетная запись в БД, чтобы сгладить пики и убрать конкуренцию запросов.
- API Gateway + Rate Limiting: единая точка входа с лимитами, чтобы внешние интеграции (DSP) не заваливали систему.
- Трассировка и мониторинг: сквозная трассировка запросов, алерты по p95/p99 и деградации, чтобы вовремя замечать узкие места.
