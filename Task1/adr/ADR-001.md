**# ADR-001. Стратегия эволюции архитектуры (от монолита к микросервисам).

**Дата:** 2026-03-15

**Статус:** Принято

#### Контекст:
Система AdScale — гибридный монолит (C++, Go, Python, Node.js) на одном инстансе PostgreSQL. Обработка запросов синхронная. 
Инфраструктура: один production-кластер, ручной деплой, нет контейнеризации.

#### Проблемы и ограничения: 
- P95 latency уже 110–120 мс (норма ≤ 100 мс). 
- Нагрузка 15000 RPS, ожидается рост до 18000 RPS. 
- Жёсткое SLA от DSP-партнёра: время ответа ≤ 80 мс, штрафы за downtime. 
- Единая БД: тяжёлые запросы аналитики и синхронная запись статистики блокируют критический путь (расчёт ставок).
- Срок: 3 месяца до интеграции с DSP. 
- Бюджет: ограничен, нет возможности полной переработки. 
- Ресурсы: нет выделенного SRE, нет аналитика для декомпозиции, архитектура не задокументирована. 
- Непрерывность бизнеса: система не должна останавливаться ни на минуту (Zero Downtime).

#### Цель: 
- Обеспечить готовность к интеграции с DSP за 3 месяца 
- Заложить фундамент для будущей микросервисной архитектуры (50000 RPS через год).

#### Рассматривались две альтернативы:
- **А1. Гибридный подход:** точечные оптимизации внутри монолита
Внедрить Redis, Read Replica и очередь сообщений, но оставить монолитную арх-ру. В будущем будет сложно выносить сервисы. 
    - Плюсы: быстро, дёшево, снижает нагрузку на БД.
    - Минусы: не решает проблему зависимостей в коде, не создает основу для выделения отдельных микросервисов
- **А2. Постепенная миграция (паттерн Strangler Fig)**
Внедрить точечные оптимизации (Redis, очереди) + начать выносить критические компоненты (Auction Engine) в отдельные сервисы через API Gateway/Feature Flags.	
    - Плюсы: улучшает SLA. Готовит к микросервисам. Оптимально в сжатых сроках.
    - Минусы: в отсутствии аналитика выделение критичных сервисов ложится на разработчика, что несет риск некорректного определения границ. Необходима настройка качественного монитотринга и процессов ci/cd.


## Решение
**Выбрана стратегия А2:** постепенная миграция на микросервисную архитектуру с использованием паттерна Strangler Fig. 
Применяются следующие архитектурные изменения:
    - критические модули Auction Engine, AdServer выделены в отдельные микросеврисы
    - взаимодействие с сервисами через Api Gateway
    - внедрение кэширования между AdServer и БД для снижения нагрузки на чтение
    - реализация read-реплики для разделения потоков записи и чтения
    - реализация очереди сообщений между statsService и БД: RabbitMq + буфферизация сообщений

## Риски
Неточное выделение критичных границ микросервисов.
Сложность в настройках сетевого взаимодействия между компонентами и маршрутизации.
