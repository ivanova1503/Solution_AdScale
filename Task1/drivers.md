### Функциональные требования к системе 
1. Обработка bid requests от DSP‑партнёра с соблюдением SLA ≤80 мс.	
2. Асинхронная запись событий статистики (клики, показы) через брокер сообщений.	
3. Изоляция аналитических запросов на отдельной read‑реплике БД.	
4. Кэширование горячих данных в Redis.	
5. Поддержка feature flags / динамической конфигурации для поэтапного включения новой логики без деплоя.	Критично для паттерна Strangler Fig и непрерывности бизнеса: можно включать новые сервисы на 1% трафика, проверять, потом увеличивать.
6. Мониторинг и алерты по ключевым метрикам (latency, error rate, queue depth).	

### Атрибуты качества (Quality Attributes) с приоритизацией
**P1. Производительность (Latency)**	P95 времени отклика ≤100 мс; для DSP‑запросов ≤80 мс.	Проигрыш аукционов, штрафы от партнёра, потеря выручки.
**P1. Доступность (Availability)** SLA 99.9%, риск прямых штрафов и репутационные потери.
**P2. Масштабируемость (Scalability)**	Возможность горизонтального масштабирования движка ставок и обработки очередей.	Рост прогнозной нагрузки до 50к prs требует возможности масштабирования.
**P2. Надёжность данных (Reliability)**	Гарантированная доставка событий статистики (at‑least‑once delivery).	Потеря данных о кликах = неверные отчёты и конфликты с рекламодателями.
**P3. Поддерживаемость (Maintainability)**	Чёткое разделение логических границ даже внутри монолита.	Подготовка к будущей миграции на микросервисы (финальное решение через год).
**P3. Наблюдаемость (Observability)**	Полные логи, трейсы запросов, метрики по компонентам.	Критично для диагностики проблем в высоконагруженной системе.
