# 3. Кеширование

## 3.1. Цели и общая стратегия

Для AdScale используется распределённый кеш на базе Redis, который снижает нагрузку на PostgreSQL и уменьшает задержки при обработке запросов ставок.

При целевой нагрузке до 50 000 RPS критически важно не выполнять синхронные запросы к основной базе данных для чтения конфигурации каждой рекламной кампании в рамках каждого аукциона.

Основные цели кеширования:

- уменьшение задержек на критическом пути аукциона;
- снижение количества запросов к PostgreSQL;
- повышение пропускной способности сервиса ставок;
- сокращение зависимости обработки ставок от доступности основной базы данных;
- обеспечение своевременного обновления конфигурации кампаний при изменении настроек.

**Основной принцип:** PostgreSQL остаётся источником истины для конфигурации кампаний и бюджетов, а Redis хранит копии данных, оптимизированные для быстрого чтения.

## 3.2. Что кешировать

| **Данные** | **Место хранения** | **Начальный TTL** | **Стратегия обновления** |
|---|---|---|---|
| Активные кампании и параметры таргетинга | Redis | 30–60 секунд | Обновление по событию `CampaignConfigUpdated` из Kafka; TTL служит дополнительной страховкой. |
| Параметры ставок и ограничения кампаний | Redis | 30–60 секунд | Инвалидация или обновление при изменении конфигурации кампании. |
| Метаданные рекламных объявлений и креативов | Redis | 5–15 минут | Обновление при изменении объявления или креатива; TTL обеспечивает ограниченное время хранения устаревшей копии. |
| Предварительно рассчитанные параметры для принятия решения о ставке | Redis или локальный кеш процесса | 1–5 секунд, если данные допускают такую задержку | Пересчёт при изменении исходной конфигурации и истечении TTL. |
| Отображаемые в интерфейсе данные о бюджете и расходах | Redis или отдельная read-модель | 1–5 секунд | Обновление событиями финансового сервиса и статистики. Только для отображения, не для финансовых решений. |
| Агрегированная статистика кампаний | ClickHouse; при необходимости Redis для часто запрашиваемых результатов | 10–60 секунд для кеша отчётов | Инвалидация по событиям или истечении TTL. Точный TTL определяется допустимой задержкой обновления отчётов. |

Указанные TTL являются стартовыми значениями для проектирования. Их необходимо уточнить по результатам нагрузочного тестирования и с учётом допустимой устарелости данных.

### Какие данные нельзя считать достоверными только по кешу

- Финансовый баланс и доступный остаток средств для проведения финансовой операции.
- Актуальный расход бюджета, если его превышение может привести к нарушению бизнес-ограничений.
- Состояние кампании, если для принятия ставки требуется немедленно учитывать её остановку или блокировку.

Для этих данных кеш может использоваться как ускоряющая проекция, но критические ограничения должны проверяться по согласованным данным или по специально спроектированному механизму резервирования бюджета. Нельзя разрешать ставку только на основании потенциально устаревшего значения бюджета.

## 3.3. Размещение Redis

Redis размещается как отдельный инфраструктурный компонент рядом с сервисом ставок в том же регионе или сетевом контуре, чтобы минимизировать сетевую задержку.

Рекомендуемая схема:

- **Redis Cluster или управляемый Redis** — распределённый кеш с горизонтальным масштабированием и отказоустойчивостью.
- **Локальный кеш в памяти сервиса ставок** — необязательный L1-кеш для наиболее часто используемых данных.
- **PostgreSQL сервиса кампаний** — постоянное хранилище и источник истины.
- **Kafka** — доставка событий об изменении конфигурации для обновления кеша.

Локальный кеш уменьшает сетевые обращения к Redis, но требует контроля версий и своевременного обновления. Он не должен быть единственным местом хранения критически важной конфигурации.

В production необходимо предусмотреть аутентификацию, шифрование сетевого трафика, сетевую изоляцию и мониторинг Redis. Для кеша также следует настроить политику вытеснения ключей, лимиты памяти и поведение при исчерпании ресурсов.

## 3.4. Стратегия инвалидации кеша

Используется комбинация событийной инвалидации и TTL.

### Основной сценарий

1. Рекламодатель изменяет параметры кампании.
2. Сервис кампаний сохраняет изменения в PostgreSQL.
3. В рамках Transactional Outbox формируется событие `CampaignConfigUpdated`.
4. Событие публикуется в Kafka.
5. Потребитель сервиса ставок получает событие и обновляет или инвалидирует соответствующие ключи Redis.
6. При следующем чтении сервис ставок получает актуальную конфигурацию и использует её при обработке аукциона.

### Правила инвалидации

- Обновлять только ключи, относящиеся к изменённой кампании, вместо очистки всего кеша.
- Использовать версию конфигурации (`configVersion`), чтобы не перезаписать новые данные более старым событием.
- Обрабатывать повторную доставку Kafka-событий идемпотентно.
- Сохранять TTL как дополнительный механизм удаления устаревших записей, даже если событие потеряно или обработано с задержкой.
- При изменении критических параметров кампании учитывать задержку доставки событий и определять, допустимо ли временное использование старой версии.

Для остановки или блокировки кампании нужен отдельный приоритетный сценарий обновления состояния. Если гарантировать своевременное получение события невозможно, система должна проверять критическое состояние по согласованному источнику или временно отказываться от ставки, когда бизнес-правила не позволяют безопасно продолжить обработку.

## 3.5. Прогрев кеша (Cache Warming)

Прогрев кеша позволяет загрузить часто используемые данные до того, как они понадобятся при высокой нагрузке.

### Сценарии прогрева

**1. При запуске сервиса ставок**

- Загрузить список активных кампаний и необходимые параметры конфигурации.
- Получить актуальные версии данных из сервиса кампаний или его хранилища через предусмотренный API/механизм доставки снимка.
- Заполнить Redis и при необходимости локальный кеш.
- Начать обработку полного потока запросов после проверки готовности критически важных данных.

**2. При изменении кампании**

- Получить событие `CampaignConfigUpdated` из Kafka.
- Обновить соответствующую запись в Redis.
- При необходимости обновить локальный кеш экземпляров сервиса ставок.

**3. Перед ожидаемым ростом нагрузки**

- Определить наиболее востребованные активные кампании по статистике использования.
- Загрузить их конфигурации в Redis заранее.
- Проверить hit ratio и задержки чтения.
- Убедиться, что прогрев не создаёт чрезмерную нагрузку на PostgreSQL.

**4. После сбоя или потери кеша**

- Восстановить данные из авторитетного источника.
- Выполнять загрузку партиями с ограничением параллелизма.
- Не направлять все запросы одновременно в PostgreSQL.
- Использовать ограниченный режим обработки, пока критические данные не восстановлены.

### Прогрев и согласованность

Для начальной загрузки желательно использовать версионированный снимок конфигурации, а после него — поток изменений из Kafka. Нужно предусмотреть согласование снимка с событиями, чтобы изменение, произошедшее во время прогрева, не было потеряно и не перезаписало более новую версию.

## 3.6. Защита от cache stampede

Cache stampede возникает, когда популярный ключ истекает, после чего множество запросов одновременно пытаются загрузить одно и то же значение из базы.

Для предотвращения проблемы применяются:

- **TTL jitter:** случайное смещение TTL, чтобы записи не истекали одновременно.
- **Single-flight:** объединение параллельных запросов на загрузку одного ключа в пределах экземпляра сервиса.
- **Stale-while-revalidate:** временное использование предыдущей версии некритичных данных, пока загружается обновление.
- **Ограничение параллелизма:** защита PostgreSQL от массовых запросов при промахах кеша.
- **Пакетная загрузка:** получение конфигураций нескольких кампаний за один запрос там, где это поддерживается.

Stale-while-revalidate разрешается только для данных, для которых допустима устарелость. Его нельзя без дополнительных гарантий использовать для решений о финансовом балансе, превышении бюджета или блокировке кампании.

## 3.7. Поведение при отказах

| **Ситуация** | **Действие системы** |
|---|---|
| Redis недоступен | Использовать локальный кеш, если он содержит подходящую по версии конфигурацию. При необходимости выполнять ограниченные обращения к основному источнику. |
| Redis и локальный кеш недоступны | Не допускать неограниченного потока запросов к PostgreSQL. Применять ограниченный fallback; если критические данные нельзя безопасно получить, возвращать no-bid. |
| Kafka временно недоступна | Повторять доставку событий после восстановления, контролировать consumer lag. Использовать TTL и сверку версий для обнаружения устаревших данных. |
| Событие пришло повторно | Обработать идемпотентно, не перезаписывая более новую версию конфигурации. |
| Кеш содержит устаревший бюджет | Не использовать его как единственное основание для разрешения финансовой операции или ставки, если это может нарушить бюджетные ограничения. |
| Массовое истечение TTL | Применять jitter, single-flight и ограничение параллельных загрузок. |

## 3.8. Мониторинг кеша

Для оценки эффективности кеширования необходимо отслеживать:

- **Cache hit ratio** — долю чтений, обслуженных кешем.
- **Latency p95/p99** — время чтения из Redis и локального кеша.
- **Evictions** — количество принудительно вытесненных ключей.
- **Memory usage** — использование и доступный объём памяти.
- **Connection errors/timeouts** — ошибки соединения и тайм-ауты.
- **Cache staleness** — возраст и версия используемой конфигурации.
- **Kafka consumer lag** — задержку доставки событий обновления.
- **Fallback rate** — частоту обращений к основному источнику вместо кеша.

Рост числа промахов кеша, задержки обновления конфигурации или fallback-запросов должен вызывать предупреждение, поскольку может привести к росту задержки критического пути аукциона.

## 3.9. Ожидаемый результат

Стратегия кеширования позволяет AdScale обслуживать часто используемые конфигурационные данные с минимальной задержкой и уменьшать нагрузку на PostgreSQL при росте трафика до 50 000 RPS.

Комбинация Redis, локального кеша, событийной инвалидации, TTL и предварительного прогрева повышает производительность и устойчивость системы. При этом PostgreSQL остаётся источником истины, а критические бизнес-ограничения не зависят исключительно от потенциально устаревших данных кеша.

Эффективность решения необходимо подтвердить нагрузочными тестами, проверяя достижение SLA критического пути аукциона до 80 мс и общей задержки p95 не более 100 мс.
