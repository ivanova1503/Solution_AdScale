# 4. Потоковая обработка данных

## 4.1. Общая архитектура

Для асинхронного обмена событиями между сервисами AdScale используется Apache Kafka. Kafka позволяет разделить обработку аукционов, сбор статистики, аналитику и финансовый учёт, не создавая жёстких синхронных зависимостей между сервисами.

Основные задачи потоковой обработки:

- сбор событий аукционов, показов и кликов;
- передача изменений конфигурации кампаний в сервис ставок;
- публикация финансовых событий для аудита и построения отчётности;
- масштабирование обработки за счёт разделов (partitions) и групп потребителей (consumer groups);
- возможность повторной обработки событий при сбоях и восстановлении сервисов.

### Основной поток данных

1. Сервис ставок и рекламный сервер генерируют события аукционов, показов и кликов.
2. События публикуются в соответствующие топики Kafka.
3. Сервис статистики потребляет события и сохраняет данные в ClickHouse.
4. Сервис аналитики независимо обрабатывает те же события в собственной группе потребителей и аналитическом контуре.
5. Сервис кампаний публикует изменения конфигурации через Transactional Outbox.
6. Сервис ставок получает изменения и обновляет Redis и локальный кеш.
7. Финансовый сервис публикует финансовые события через Transactional Outbox для аудита и обновления аналитических проекций.

Kafka используется для асинхронной обработки, но не заменяет синхронные проверки, необходимые для принятия критических решений в аукционе или проведения финансовых операций.

## 4.2. Топики Kafka

Для событий используются отдельные топики с версионируемыми именами.

| **Топик** | **Производитель** | **Потребители** | **Ключ сообщения** | **Назначение** |
|---|---|---|---|---|
| `adscale.auction-events.v1` | Сервис ставок / Auction Engine | Statistics Service, Analytics Service | `auctionId` | Результаты аукционов, решения о ставках, причины отказа от ставки и технические метрики обработки. |
| `adscale.impressions.v1` | AD Server / Delivery Service | Statistics Service, Analytics Service | `eventId` или `auctionId` | События показов рекламы и данные для расчёта показателей кампаний. |
| `adscale.clicks.v1` | Delivery Service | Statistics Service, Analytics Service | `eventId` или `auctionId` | События кликов, необходимые для расчёта CTR и других метрик эффективности. |
| `adscale.campaign-config.v1` | Campaign Service | Bidding Service | `campaignId` | Изменения конфигурации кампаний, таргетинга, статусов и параметров ставок. |
| `adscale.financial-events.v1` | Financial Service | Аналитические проекции, аудит | `accountId` | Финансовые операции, изменения учётных записей и события для сверки и отчётности. |
| `adscale.dead-letter.v1` | Сервисы-потребители | Операционная поддержка, контролируемые процессы повторной обработки | Исходный ключ или `eventId` | Сообщения, которые не удалось обработать после исчерпания допустимых повторных попыток. |

### Правила выбора ключей

- Для `adscale.auction-events.v1` ключ `auctionId` позволяет сохранять порядок событий одного аукциона в пределах раздела.
- Для `adscale.campaign-config.v1` ключ `campaignId` сохраняет порядок изменений одной кампании в пределах раздела.
- Для финансовых событий ключ `accountId` помогает сохранять порядок операций одного счёта.
- Для событий показов и кликов ключ выбирается по характеру потребления: `eventId` обеспечивает распределение отдельных событий, а `auctionId` помогает группировать связанные события. При использовании одного ключа необходимо оценивать риск неравномерной нагрузки.

Kafka гарантирует порядок сообщений только внутри одного раздела, а не во всём топике.

## 4.3. Схема событий: Avro и JSON

Для production-среды рекомендуется **Avro совместно со Schema Registry**. Такая схема позволяет централизованно управлять версиями событий, проверять совместимость и уменьшать размер сообщений по сравнению с текстовым JSON.

JSON допустим на раннем этапе разработки или для простых интеграций, если валидация и правила совместимости обеспечиваются отдельно.

### Общая структура события

Каждое сообщение должно содержать метаданные и полезную нагрузку (payload).

Пример логической структуры события:

```json
{
  "eventId": "evt-12345",
  "eventType": "CampaignConfigUpdated",
  "schemaVersion": 1,
  "occurredAt": "2026-10-10T12:00:00Z",
  "producer": "campaign-service",
  "correlationId": "corr-67890",
  "campaignId": "cmp-1001",
  "payload": {
    "status": "ACTIVE",
    "configVersion": 42,
    "bidLimit": 15.5
  }
}
```

Пример приведён для иллюстрации структуры; фактическая схема должна определяться контрактом конкретного типа события.

### Назначение полей

| **Поле** | **Назначение** |
|---|---|
| `eventId` | Уникальный идентификатор события для дедупликации и идемпотентной обработки. |
| `eventType` | Тип события, например `AuctionCompleted` или `CampaignConfigUpdated`. |
| `schemaVersion` | Версия схемы события. |
| `occurredAt` | Время возникновения события в UTC. |
| `producer` | Сервис, создавший событие. |
| `correlationId` | Идентификатор для связи событий одного бизнес-процесса и распределённой трассировки. |
| `campaignId` / `auctionId` / `accountId` | Идентификаторы сущностей предметной области в зависимости от типа события. |
| `payload` | Данные конкретного события. |

### Правила управления схемами

1. Каждому типу событий соответствует отдельная схема.
2. Изменения схем должны сохранять обратную совместимость, если потребители обновляются независимо.
3. Новые необязательные поля добавляются с безопасными значениями по умолчанию.
4. Удаление и переименование полей выполняются через контролируемую миграцию версий.
5. Производители и потребители проходят проверку совместимости схем в CI/CD.
6. В сообщения не включаются секреты, платёжные реквизиты и избыточные персональные данные.

## 4.4. Группы потребителей

Каждый независимый сервис обработки использует собственную consumer group. Благодаря этому статистика и аналитика получают события независимо друг от друга, а замедление одного потребителя не блокирует другой.

| **Consumer group** | **Топики** | **Задачи** |
|---|---|---|
| `statistics-service` | `adscale.auction-events.v1`, `adscale.impressions.v1`, `adscale.clicks.v1` | Обработка событий и запись статистики в ClickHouse. |
| `analytics-service` | `adscale.auction-events.v1`, `adscale.impressions.v1`, `adscale.clicks.v1`, `adscale.financial-events.v1` | Построение аналитических моделей, агрегатов и отчётов. |
| `bidding-config-consumer` | `adscale.campaign-config.v1` | Обновление Redis и локального кеша конфигурации ставок. |
| `financial-audit-consumer` | `adscale.financial-events.v1` | Передача финансовых событий в аудит и формирование отчётных проекций без изменения авторитетного финансового учёта. |
| `dead-letter-processor` | `adscale.dead-letter.v1` | Контроль ошибок, анализ сообщений и запуск контролируемой повторной обработки. |

Количество экземпляров потребителей масштабируется с учётом количества разделов топика и фактической нагрузки. В рамках одной consumer group один раздел в конкретный момент назначается не более чем одному активному потребителю.

Для повышения пропускной способности необходимо контролировать количество разделов, задержку потребления и равномерность распределения ключей.

## 4.5. Гарантии доставки и обработка ошибок

Для большинства потоков используется модель **at-least-once**: сообщение может быть доставлено повторно, поэтому потребители должны поддерживать идемпотентность.

Основные механизмы надёжности:

- **Idempotent consumers:** повторная обработка события не должна приводить к повторному учёту одного и того же бизнес-факта.
- **Дедупликация:** используется `eventId` или другой стабильный идентификатор события.
- **Retry:** временные ошибки обрабатываются ограниченным количеством повторных попыток с экспоненциальной задержкой и jitter.
- **Dead Letter Queue (DLQ):** после исчерпания повторных попыток сообщение переводится в DLQ с информацией об ошибке.
- **Transactional Outbox:** изменение в PostgreSQL и запись о событии фиксируются в одной транзакции; отдельный механизм публикации отправляет событие в Kafka.
- **Контролируемый replay:** после устранения ошибки события могут быть повторно обработаны с контролем дубликатов и побочных эффектов.

Kafka-транзакции и идемпотентный producer сами по себе не гарантируют exactly-once обработку между Kafka и внешней базой данных. Для записи в ClickHouse и PostgreSQL необходимо отдельно продумать дедупликацию, повторную обработку и согласованность результата.

Для финансовых операций Kafka не является заменой финансового реестра. Источником истины остаётся Financial Service и его транзакционная база данных.

## 4.6. Политика хранения сообщений

Срок хранения зависит от назначения топика, объёма потока и требований к восстановлению.

| **Топик** | **Начальный срок хранения** | **Дополнительные настройки** |
|---|---|---|
| `adscale.auction-events.v1` | 7–14 дней | Повторная обработка и расследование ошибок. |
| `adscale.impressions.v1` | 7 дней | Восстановление статистики за ограниченный период. |
| `adscale.clicks.v1` | 7 дней | Повторная обработка событий и сверка статистики. |
| `adscale.campaign-config.v1` | 7 дней | При необходимости — compacted topic для хранения последнего состояния по `campaignId`. |
| `adscale.financial-events.v1` | 30 дней или больше по требованиям аудита | Длительность определяется политикой хранения, требованиями комплаенса и возможностями архивации. |
| `adscale.dead-letter.v1` | 14–30 дней | Срок должен обеспечивать расследование и контролируемую повторную обработку. |

Эти сроки являются стартовыми параметрами и должны быть уточнены после оценки объёма событий, требований к восстановлению и стоимости хранения.

Для топика конфигурации кампаний можно использовать compaction, чтобы сохранять последнее состояние по ключу. Однако compaction не заменяет журнал изменений, если требуется история всех версий конфигурации.

Для production рекомендуется репликация разделов с коэффициентом не менее 3 при наличии достаточного числа брокеров, настройка `acks=all` и `min.insync.replicas`. Конкретные параметры определяются требованиями к доступности и допустимой потере данных.

Kafka retention не заменяет резервное копирование баз данных или долговременный архив событий. Если необходимо восстановление за период, превышающий срок хранения Kafka, данные следует архивировать в отдельное хранилище.

## 4.7. Мониторинг и эксплуатация

Для контроля потоковой обработки отслеживаются:

- **Consumer lag** — отставание групп потребителей от последних сообщений.
- **Throughput** — количество сообщений в секунду для каждого топика.
- **Processing latency** — задержка от возникновения события до завершения обработки.
- **Error rate** — доля сообщений, завершившихся ошибкой.
- **DLQ volume** — количество сообщений в очереди ошибок.
- **Under-replicated partitions** — разделы с недостаточным числом актуальных реплик.
- **Broker disk usage** — заполнение дисков брокеров.
- **Schema validation errors** — сообщения, не соответствующие зарегистрированной схеме.

При росте consumer lag необходимо проверять производительность потребителей, равномерность ключей, число разделов и скорость записи в целевое хранилище.

## 4.8. Ожидаемый результат

Использование Kafka позволяет AdScale асинхронно обрабатывать события аукционов, показов, кликов, кампаний и финансовых операций. Раздельные consumer groups обеспечивают независимое масштабирование статистики и аналитики, а схемы Avro и Schema Registry упрощают управление контрактами между сервисами.

Сочетание репликации, идемпотентных потребителей, Transactional Outbox, контролируемых повторных попыток и DLQ повышает надёжность потоковой обработки. Окончательные параметры количества разделов, репликации и сроков хранения должны подтверждаться нагрузочными тестами и требованиями к восстановлению данных.
