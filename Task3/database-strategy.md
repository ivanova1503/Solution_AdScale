# Database Strategy — AdScale

## 1. Database per Service

### 1.1. Стратегия выбора баз данных

Для AdScale применяется принцип **Database per Service**: каждый сервис владеет своими данными и управляет ими самостоятельно. Другие сервисы не обращаются напрямую к его базе данных, а получают необходимую информацию через API или события Kafka.

Такой подход позволяет независимо масштабировать сервисы, выбирать оптимальное хранилище для каждого типа нагрузки и изолировать сбои.

| **Сервис** | **Тип базы данных** | **Обоснование** |
| :--- | :--- | :--- |
| Сервис ставок (Bidding Service) | PostgreSQL + Redis | PostgreSQL хранит правила ставок, настройки и другие структурированные данные, требующие надёжного хранения. Redis обеспечивает быстрый доступ к часто используемым данным и настройкам в критическом пути аукциона. Чтение конфигурации из кэша позволяет сократить задержки и уменьшить нагрузку на PostgreSQL. |
| Сервис кампаний (Campaign Service) | PostgreSQL | Реляционная база данных подходит для хранения кампаний, бюджетов, таргетингов и настроек рекламодателей. Транзакции и ограничения целостности помогают поддерживать согласованность данных при создании и изменении кампаний. Обновления публикуются в Kafka для синхронизации конфигурации с сервисом ставок. |
| Сервис статистики (Statistics Service) | ClickHouse | Сервис обрабатывает большие объёмы событий показов, кликов и результатов аукционов. Колоночное хранение и аналитические SQL-запросы обеспечивают эффективную агрегацию данных и построение отчётов по времени, кампаниям и рекламодателям. |
| Сервис аналитики (Analytics Service) | ClickHouse + объектное хранилище (S3-совместимое) | ClickHouse используется для аналитических запросов, построения агрегатов и анализа больших массивов данных. Объектное хранилище подходит для длительного хранения сырых событий и исторических данных в форматах, например, Parquet. Отдельный аналитический контур изолирует ресурсоёмкие запросы от оперативных сервисов. |
| Сервис финансов (Financial Service) | PostgreSQL | Финансовые операции требуют транзакционности, целостности и надёжного учёта. PostgreSQL поддерживает ACID-транзакции, ограничения целостности и уникальные ключи для защиты от повторной обработки операций. Балансы и финансовые проводки хранятся в авторитетной базе сервиса. Redis не используется как источник истины для финансовых решений. |
