# 2. Масштабирование баз данных

## 2.1. Общая стратегия

Для масштабирования баз данных AdScale применяется комбинация вертикального и горизонтального масштабирования, репликации, шардирования и CQRS (Command Query Responsibility Segregation).

Основные принципы:

- **Репликация** — повышение доступности и распределение нагрузки чтения.
- **Шардирование** — горизонтальное распределение данных между несколькими узлами при росте объёма данных и нагрузки.
- **Read replicas** — выполнение запросов чтения на репликах, чтобы снизить нагрузку на основной узел.
- **CQRS** — разделение операций изменения данных и операций чтения, особенно для сервисов с высокой нагрузкой на чтение и аналитических запросов.

Шардирование не включается автоматически на старте. Сначала используются индексы, оптимизация запросов, репликация и партиционирование. Шардирование вводится при подтверждённой необходимости по результатам мониторинга и нагрузочного тестирования.

## 2.2. Стратегия масштабирования по сервисам

| **Сервис** | **Репликация** | **Стратегия шардирования** | **Read replicas / CQRS** |
|---|---|---|---|
| Сервис ставок (Bidding Service) | PostgreSQL primary + replica для служебных запросов и восстановления. Redis Cluster для масштабирования кэша при необходимости. | При необходимости — по `campaignId` или `advertiserId`. Применять только при росте объёма конфигурационных данных и нагрузки на запись. | Основной путь обработки ставок использует Redis или локальный кэш. Реплики PostgreSQL не используются для критических решений, если возможна задержка репликации. CQRS — для отделения управления конфигурацией от её быстрого чтения. |
| Сервис кампаний (Campaign Service) | PostgreSQL primary + read replicas для распределения запросов чтения. | По `advertiserId` или `tenantId`, чтобы данные одного рекламодателя находились в одном шарде. | Read replicas подходят для интерфейса рекламодателя и отчётных запросов. CQRS — команды изменения кампаний выполняются в PostgreSQL, а события Kafka обновляют read-модели и кэш сервиса ставок. |
| Сервис статистики (Statistics Service) | Репликация ClickHouse для доступности и распределения аналитических запросов между узлами. | Партиционирование по дате события; распределение данных по `campaignId`, `advertiserId` или хешу `eventId` в зависимости от основных запросов. | Реплики ClickHouse используются для распределения запросов чтения. Агрегированные представления и предварительные вычисления ускоряют построение статистики. |
| Сервис аналитики (Analytics Service) | Репликация ClickHouse в отдельном аналитическом контуре. При необходимости — резервное копирование данных в объектное хранилище. | Партиционирование по времени и распределение по ключу, соответствующему аналитическим запросам, например `advertiserId` или `campaignId`. | **Да, read replicas применимы**, если они помогают распределять тяжёлые аналитические запросы. Для изоляции нагрузки предпочтительнее отдельный кластер ClickHouse, а не чтение из рабочих баз транзакционных сервисов. CQRS реализуется через отдельные аналитические модели и агрегаты. |

CQRS — для отделения финансовых команд от отчётных read-моделей. |

## 2.3. Master-slave репликация

Для PostgreSQL используется схема **primary-replica** (традиционно также называемая master-slave):

- **Primary** принимает операции записи и обеспечивает выполнение транзакций.
- **Replica** получает изменения с primary и обслуживает подходящие запросы чтения.
- При отказе primary выполняется переключение на новый primary согласно выбранной стратегии высокой доступности.

Репликация PostgreSQL обычно асинхронная, поэтому чтение с реплики может возвращать устаревшие данные. Для операций, требующих немедленной согласованности, чтение выполняется с primary либо применяется механизм проверки актуальности данных.

Для ClickHouse используется собственная модель репликации и распределения данных. Она настраивается с учётом требований к доступности, объёма данных и параллельной обработке запросов.

Redis Cluster позволяет распределять ключи кэша между узлами. При этом Redis не заменяет репликацию и резервное копирование основных баз данных.

## 2.4. Стратегия шардирования

Шардирование применяется при достижении пределов масштабирования одного узла. Ключ выбирается с учётом характера запросов, равномерности распределения данных и необходимости выполнять транзакции в пределах одного шарда.

| **Тип данных** | **Предлагаемый ключ** | **Обоснование** |
|---|---|---|
| Кампании и настройки рекламодателей | `advertiserId` или `tenantId` | Позволяет хранить связанные данные рекламодателя вместе и выполнять основные запросы без обращения ко всем шардам. |
| Конфигурация ставок | `campaignId` или `advertiserId` | Подходит для распределения конфигурационных данных, если одного узла становится недостаточно. Для критического пути предпочтительно кэширование. |
| События аукционов | `auctionId` или хеш `auctionId` | Позволяет равномерно распределять события и обрабатывать данные аукционов независимо. |
| События показов и кликов | Дата события + ключ распределения, например хеш `campaignId` | Партиционирование по дате упрощает удаление и архивирование старых данных; ключ распределения обеспечивает параллельную обработку. |
| Аналитические данные | Дата события + `advertiserId` или `campaignId` | Соответствует типичным фильтрам и группировкам аналитических запросов. |
| Финансовые операции | `accountId` или `tenantId` | Сохраняет операции одного счёта в одном шарде и упрощает обеспечение согласованности. |

### Дополнительные правила

1. Для PostgreSQL шардирование должно учитывать внешние связи, уникальность идентификаторов и границы транзакций.
2. Для ClickHouse в первую очередь настраиваются партиционирование и ключ сортировки `ORDER BY`. Партиционирование по времени и распределение по шардам решают разные задачи.
3. Необходимо избегать горячих шардов, когда один рекламодатель или одна кампания создаёт непропорционально большую нагрузку.
4. При выборе ключа учитываются основные шаблоны запросов: фильтрация, группировка, соединения и диапазоны дат.
5. До внедрения шардирования необходимо измерить загрузку CPU, дисковую подсистему, задержки запросов, объём данных и темп их роста.

## 2.5. Read replicas для аналитики

Для AdScale аналитическая нагрузка отделяется от транзакционной. Сервис аналитики использует собственный контур ClickHouse, получающий события через Kafka или данные из специализированного хранилища.

Read replicas ClickHouse целесообразны, если:

- увеличивается количество одновременных аналитических запросов;
- отчёты конкурируют за ресурсы с загрузкой и агрегацией данных;
- требуется повысить доступность аналитического контура;
- один узел перестаёт обеспечивать требуемое время ответа.

Если статистика и аналитика создают разные профили нагрузки, их рекомендуется размещать в отдельных кластерах или изолированных вычислительных контурах. Это предотвращает влияние тяжёлых аналитических запросов на оперативные отчёты.

## 2.6. CQRS — разделение команд и запросов

CQRS применяется там, где операции записи и чтения имеют существенно разные требования к производительности и структуре данных.

### Сервис кампаний

- **Command-модель:** PostgreSQL — создание и изменение кампаний, бюджетов, таргетингов и настроек.
- **Query-модель:** read replicas, кэш или отдельные проекции для отображения конфигурации.
- **Обмен:** после изменения кампании сервис публикует событие через Transactional Outbox в Kafka. Потребители обновляют локальные представления и кэш.

### Сервис ставок

- **Command-модель:** управление конфигурацией ставок и бизнес-правилами через сервис кампаний или соответствующий административный интерфейс.
- **Query-модель:** Redis и локальный кэш для быстрого чтения актуальной конфигурации.
- **Результат:** критический путь аукциона не зависит от синхронных запросов к основной базе при каждом запросе ставки.

### Сервисы статистики и аналитики

- **Запись:** получение и обработка событий из Kafka.
- **Чтение:** агрегированные таблицы, материализованные представления и аналитические запросы в ClickHouse.
- **Результат:** тяжёлые запросы выполняются независимо от транзакционных операций.

### Финансовый сервис

- **Command-модель:** PostgreSQL — проведение финансовых операций, учёт проводок и обработка ключей идемпотентности.
- **Query-модель:** read replicas или отдельные проекции для истории операций и отчётов.
- **Ограничение:** отчётная модель может обновляться с задержкой, но не должна подменять авторитетные данные при выполнении финансовых операций.

CQRS и асинхронные события могут приводить к временной рассогласованности read-модели. Поэтому необходимо определить допустимую задержку обновления, правила повторной обработки событий и механизм восстановления проекций.

## 2.7. Этапы внедрения масштабирования

1. **Начальный этап:** индексы, оптимизация запросов, мониторинг, резервное копирование и настройка кэша.
2. **Рост нагрузки:** репликация PostgreSQL, масштабирование Redis и ClickHouse, предварительная агрегация статистики.
3. **Разделение нагрузки:** выделение отдельного аналитического контура и внедрение CQRS там, где это оправдано.
4. **Горизонтальное масштабирование:** шардирование отдельных хранилищ при подтверждённой необходимости.
5. **Эксплуатационная устойчивость:** регулярные тесты восстановления, проверка переключения реплик, контроль задержки репликации и мониторинг горячих шардов.

## 2.8. Ожидаемый результат

Стратегия масштабирования позволяет AdScale расти от текущей нагрузки около 15 000 RPS к целевым 50 000 RPS без необходимости одинаково масштабировать все хранилища. Репликация распределяет чтение, шардирование помогает увеличивать пропускную способность и объём хранения, а CQRS изолирует оперативные операции от ресурсоёмких запросов.

Выбор количества реплик, ключей шардирования и параметров хранения должен быть подтверждён нагрузочным тестированием. Целевые показатели — SLA критического пути аукциона до 80 мс и общая задержка p95 не более 100 мс.
