# AdScale — стратегия данных, масштабирования и отказоустойчивости

## 1. Описание проекта

AdScale — микросервисная рекламная платформа для обработки запросов на показ рекламы, проведения аукционов, управления рекламными кампаниями, учёта финансовых операций и формирования аналитической отчётности.

Цель проектирования — обеспечить горизонтальное масштабирование, отказоустойчивость хранилищ и высокую производительность при росте рекламного трафика.

Целевые показатели критичного пути аукциона:
- SLA по времени отклика — до 80 мс.
- Поддержка роста входящего трафика до 50 000 RPS.
- Изоляция аналитических запросов от критичного пути аукциона.
- Сохранение целостности финансовых операций при сбоях.

Указанные значения являются целевыми архитектурными показателями и должны подтверждаться нагрузочным тестированием.

## 2. Основные архитектурные решения

- **Database per Service.** Каждый микросервис владеет собственной базой данных и управляет её схемой независимо. Прямой доступ к базам других сервисов запрещён.
- **PostgreSQL для транзакционных данных.** Используется для управления кампаниями, хранения правил ставок и финансовых операций.
- **ClickHouse для статистики и аналитики.** Колонночные хранилища обеспечивают эффективную обработку больших объёмов событий и аналитических запросов. Контуры статистики и аналитики разделены для изоляции нагрузки.
- **Redis для кеширования.** Горячая конфигурация кампаний и другие безопасные для кеширования данные доступны без обращения к SQL-базе на каждом аукционе. Redis не является источником истины для финансового баланса.
- **Apache Kafka для потоковой обработки.** События показов, кликов, аукционов, изменений кампаний и финансовых операций передаются асинхронно.
- **Репликация и резервное копирование.** Реплики повышают доступность и производительность чтения; резервные копии и проверенные процедуры восстановления обеспечивают защиту от потери данных.
- **Паттерны надёжности.** Circuit Breaker, ограниченные повторные попытки с экспоненциальной задержкой, идемпотентная обработка и резервные стратегии снижают влияние сбоев.

## 3. Стратегия работы с данными

Транзакционные данные обрабатываются в базах соответствующих сервисов. Для финансовых операций применяется ACID-транзакционность и защита от повторного выполнения.

События передаются через Kafka и обрабатываются независимыми группами потребителей. Статистика и аналитика используют собственные хранилища, поэтому тяжёлые запросы и агрегации не создают дополнительную нагрузку на базы критичного пути.

Кеширование уменьшает задержки при получении конфигурации кампаний. Обновления распространяются через события, а TTL и версии данных помогают контролировать актуальность кеша.
